## Что защищено в коде

- API-ключи используются только сервером через переменные окружения. Они не
  должны находиться в HTML, JavaScript браузера, APK, SQL, Git или переписке.
- `.gitignore` исключает окружение, ключи подписи, сертификаты и резервные копии.
  Проверка `npm run security:secrets` блокирует известные шаблоны секретов в
  текущих файлах. Поиск по шаблонам не гарантирует отсутствие всех секретов.
- Пароли хешируются scrypt. Их нельзя и не нужно расшифровывать.
- Серверные токены сессий и восстановления хранятся в БД как SHA-256-хеши
  случайных 256-битных значений, а не открытые токены.
- Медицинские поля шифруются AES-256-GCM с новым случайным IV для каждой записи.
  Проверка подлинности связывает шифротекст с таблицей, ID строки и полем.
  Подмена между строками, потерянный ключ или повреждение приводят к отказу
  чтения, а не выдаче непроверенного содержимого.

Покрытые поля:

| Таблица | Поля |
| --- | --- |
| appointments | message, diagnosis, notes, treatment |
| analyses | type, results |
| prescriptions | medicine, dosage, instructions |
| chat_messages | text |
| users | blood_type |

**Это не шифрование всей базы.** ИИН, имя, email, связи участников, даты,
статусы, интервалы приёма, расписания и журнал действий остаются доступными
оператору БД. Они тоже чувствительны. Для шифрования идентификаторов нужно
отдельно изменить поиск, уникальность и связи старых записей, например с
серверными индексами поиска по HMAC. Простая замена ИИН шифротекстом сломает
проверку прав. Такое изменение сейчас не реализовано.

Шифрование БД не защищает от скомпрометированного сервера, имеющего ключи,
от ошибочного предоставления доступа или от раскрытия данных пользователем.
Ключи нужно хранить отдельно от БД, ограничивать доступ к ним и резервировать.
Основание: [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html).

## Ключи шифрования

### Создание защищённой копии на этом компьютере

В Windows PowerShell:

```powershell
& 'C:\AndroidProjects\qamqormed-app\scripts\Initialize-DataKeys.ps1'
```

Скрипт дважды запросит скрытым вводом длинную уникальную парольную фразу
(не менее 16 символов). Сохраните её в менеджере паролей; не отправляйте в чат.
Он создаст 32 случайных байта, проверит обратное чтение зашифрованной копии
и ограничит права папки текущим пользователем Windows и SYSTEM.

- `C:\Users\bolat\AppData\Local\QamqorMed\secrets\data-keys.vault.json`:
  переносимая зашифрованная копия (AES-256-GCM, ключ из парольной фразы через scrypt).
  Сохраните её дополнительно в независимом защищённом месте. Одной локальной
  копии недостаточно при потере компьютера.
- `C:\Users\bolat\AppData\Local\QamqorMed\secrets\data-keys.dpapi`:
  рабочая копия, защищённая Windows DPAPI CurrentUser. Она привязана к профилю
  Windows и не заменяет переносимую резервную копию.

Скрипт не выводит ключи и не перезаписывает существующие файлы. При ошибке
сохраните созданные файлы до проверки, не запускайте генерацию поверх них.
Для проверки окружения без генерации ключей доступен параметр `-CheckOnly`.
Повышенные права администратора не требуются: права папки устанавливаются
через .NET только для изменяемых разделов ACL, без изменения аудита Windows.

### Добавление в Netlify

После успешного теста на изолированной ветке операторский скрипт
`Invoke-Operator.ps1 -Action set-keys` создаёт `QAMQOR_DATA_KEY_ID` и
`QAMQOR_DATA_KEYS` через авторизованный Netlify CLI. Ключи расшифровываются
только в памяти и передаются дочернему процессу через stdin, не через аргументы.
Значения не выводятся в терминал и не попадают в Git. Существующие переменные
этот скрипт не заменяет: смена ключа требует отдельной процедуры.

Обе переменные создаются как секретные, только для **Production**; область
включает **Functions** и **Builds** (а также Runtime, совместимо с текущими
настройками аккаунта). Preview/Branch/Local Development остаются без этих ключей.
Скрипт проверяет ID проекта и соответствие ключа успешному тестовому прогону.
Это подготовленный способ добавления, не подтверждение выполненной настройки.

Серверу нужны:

- `QAMQOR_DATA_KEY_ID`: имя активного ключа, например `data-v1`.
- `QAMQOR_DATA_KEYS`: JSON-объект, сопоставляющий имена ключей их значениям.
  Каждое значение должно быть 32 криптографически случайными байтами в base64.
- `NETLIFY_DATABASE_URL`: существующее защищённое подключение к нужной базе.

Формат: `{"data-v1":"<base64 от 32 случайных байт>"}`. Это описание формата,
не готовый ключ. Пароль человека, UUID и публичный пример ключом не являются.
Генерируйте ключ локально криптографическим генератором и сохраняйте в
менеджере секретов, не в репозитории. Для этого проекта владелец уже выполнил
`Initialize-DataKeys.ps1`; повторно генерировать ключи для существующей БД нельзя.

Задайте переменные в секретных настройках нужного контекста Netlify: Functions
для API и Builds для проверки публикации. Не переносите их в `netlify.toml` и
переменные, встраиваемые в браузерный bundle. Не выдавайте production-секреты
непроверенным веткам/preview-сборкам. Обновление окружения функций требует
проверенной новой публикации.

Сохраните независимую защищённую копию ключей и проверьте восстановление.
**Потеря ключа делает зашифрованные данные недоступными.** Для ротации добавьте
новый ключ в JSON и измените активный ID. Старые ключи нужны, пока существуют
старые шифротексты или резервные копии. Не удаляйте их после одной сборки.

## Порядок переноса

Сначала выполните весь процесс на изолированной тестовой базе. Копия рабочей
базы тоже содержит персональные данные: не передавайте её в чат и не публикуйте.

1. Проверьте возможность восстановления резервной копии, доступность старых
   ключей, список затронутых сервисов и процедуру отката.
2. На время переноса остановите чтение и запись через старые версии сайта/API,
   Android, фоновые задания и другие подключения. Старая версия не умеет
   читать новый шифротекст и может вновь записывать открытый текст.
3. Проверьте ветку и базу. Выполните целиком, в этом порядке:
   `20260924_sessions_prescriptions.sql`, `20260924_roles_audit.sql`,
   `20260925_data_protection.sql`, `20261109_encrypted_field_capacity.sql`.
   Последний файл расширяет старое поле `appointments.diagnosis` с VARCHAR(255)
   до TEXT: шифротекст длиннее исходного текста. Проверка сборки требует TEXT
   для всех шифруемых текстовых полей. Уже установленные миграции проверяйте
   по реальной схеме и служебным отметкам, не переписывайте их историю.
   При уже выполненном первом файле не нужно
   добавлять вручную его служебную отметку. При конфликте остановитесь, не
   удаляйте пациентов и медицинские записи ради прохождения миграции.
4. SQL-файлы обновляют только схему, включая восстановление и ёмкость полей.
   **Они не шифруют старые данные и не меняют пароли.**
5. В доверенной локальной оболочке настройте серверные переменные окружения
   без записи секретов в историю команд. Инструмент не читает `.env`
   автоматически. Убедитесь, что выбран именно тестовый hostname.
6. Из корня репозитория запустите проверку без изменений:

```powershell
node scripts/encrypt-clinical-data.mjs --confirm-host "<hostname выбранной базы>"
```

7. Проверьте результат. Скрипт сообщает только названия таблиц и количество
   записей; содержимое, URL подключения и ключи не выводятся. При ошибке он
   завершится без диагностического текста драйвера, который может содержать
   секреты. Диагностируйте структуру и настройки в защищённой среде.
8. После подтверждения резервной копии и остановки записи выполните перенос:

```powershell
node scripts/encrypt-clinical-data.mjs --confirm-host "<hostname выбранной базы>" --apply --maintenance-confirmed --backup-confirmed
```

9. Перенос идёт пакетами по 200 строк. Каждый пакет сверяет исходные значения,
   проверяет расшифровку и выполняется транзакционно. Уже завершённые пакеты
   сохраняются при последующей ошибке. Сохраните ключи и повторите перенос
   после устранения причины; не восстанавливайте старое приложение поверх
   частично зашифрованной базы.
10. Для `appointments` инструмент блокирует таблицу и временно выключает
    только запрет изменения завершённой записи внутри транзакции, затем
    включает его перед COMMIT. Ошибка откатывает и данные, и изменение триггера.
    Нужна отдельная роль оператора миграций с ALTER; обычному API такие права
    давать не следует. Работа настоящих блокировок требует проверки на PostgreSQL.
11. Повторите сухой прогон: ожидается `would_encrypt=0` для всех таблиц.
    Он также проверит подлинность уже зашифрованных значений имеющимися ключами.
12. Уберите `QAMQOR_ALLOW_LEGACY_PLAINTEXT` из обычного окружения. Это временный
    совместимый режим чтения, не защита. Проверка публикации запрещает значение
    `true`. Новые записи никогда не сохраняются открытым текстом этим режимом.
13. Запустите `npm run db:check` с выбранным подключением. Проверка не изменяет
    данные; проверяет схему, ёмкость полей, отсутствие открытых медицинских
    значений и формат scrypt у всех активных аккаунтов без вывода значений.
    Выявлено 43 активных аккаунта со старым/неверным форматом пароля: 36 врачей,
    1 администратор, 6 пациентов. Перед выпуском нужен доверенный перенос
    паролей в scrypt; ранее раскрытые пароли необходимо именно заменить,
    а не только хешировать. Сессии таких аккаунтов должны быть отозваны.
    Автоматически отключать аккаунты или назначать всем один пароль нельзя.
    Она не заменяет проверку расшифровки всех записей и тест восстановления.
14. Проверьте логин, роли, собственные/чужие медданные, назначения, чат,
    восстановление, журнал действий и новый Android против тестового API.
    Только после устранения блокеров согласуйте такое же окно для рабочей среды.

Снимки, WAL, резервные копии и старые ветки могут сохранять исходные открытые
данные. Перенос текущих строк не стирает эти копии. Нужны отдельные правила
доступа, срока хранения и безопасного удаления. Не удаляйте единственную
проверенную резервную копию до завершения переноса.

## Восстановление без рассылки

- Только активный **пациент** отправляет email и ИИН. Публичный ответ одинаков
  также для неверных данных и сотрудников; запрос ограничен по частоте.
- Браузер получает защищённую HttpOnly-cookie; Android хранит случайный токен
  запроса через Android Keystore. Простого знания email и ИИН для завершения
  процедуры недостаточно: нужен этот токен и одобрение администратора.
- Администратор видит очередь, подтверждает собственный пароль и риск, затем
  одобряет или отклоняет. Он не задаёт новый пароль пациента и не видит токен.
- Пациент проверяет ответ в исходном браузере/установке приложения. При
  одобрении появляется форма нового пароля. Запрос ожидает до 24 часов;
  после одобрения окно составляет не более 15 минут.
- Успешная смена одноразово расходует запрос, отзывает все сессии и другие
  ожидающие запросы, записывает событие аудита. Затем нужен обычный вход.
- Для врача и администратора этот путь недоступен. Нужен отдельный доверенный
  процесс восстановления оператора. Коды по email и автоматические письма
  не отправляются. Смена браузера/очистка данных требует нового запроса.

**Одобрение запроса не доказывает личность.** Злоумышленник может знать чужие
email/ИИН и отправить запрос со своего устройства. Если администратор ошибётся,
атакующий получит аккаунт. Не одобряйте только по совпадению этих полей.
Пользователь согласовал упрощённый hobby-сценарий, но он не подходит для
реальных медицинских данных без независимой проверки владельца.
Это ограничение, а не подключённая проверка почты, eGov или удостоверения.
См. [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## Проверки и публикация

Без рабочих секретов: `npm ci`, `npx playwright install chromium`, `npm test`,
`npm run security:secrets`, `npm audit`, `npm run build`.
`npm run security:history` намеренно остаётся с находкой до согласованной
очистки истории; отзыв ключа нельзя определить локальным поиском по Git.

Проверки используют искусственные данные, не рабочую Neon. См. актуальные
результаты и оставшиеся ограничения в `SECURITY-WORK-IN-PROGRESS.md`.
Успешная локальная сборка не подтверждает прохождение всех проверок безопасности.
Текущий статус переноса и публикации ведётся отдельно, а не определяется наличием SQL-файлов.
Актуальные результаты: [RELEASE-READINESS-2026-11-09.md](RELEASE-READINESS-2026-11-09.md).

## Локальные копии оператора

Защищённая папка: `%LOCALAPPDATA%\QamqorMed\secrets`, вне Git и OneDrive.
`data-keys.vault.json` открывается парольной фразой владельца; `data-keys.dpapi`
доступен только тому же пользователю Windows. Не удаляйте ни одну копию.
`production-source.vault.json` содержит предмиграционные строки 11 таблиц,
`production-access.vault.json` содержит подключения оператора и ограниченной
серверной роли, `production-credentials.vault.json` содержит новые тестовые пароли.
Эти файлы шифруются ключом из защищённого хранилища. Без ключей восстановление
невозможно; JSON-копия строк не заменяет PostgreSQL-снимок схемы и ограничений.

Скопируйте **зашифрованные** файлы на независимый защищённый носитель; парольную
фразу храните отдельно в менеджере паролей. Значения не нужны в чате или Git.
Операционные команды привязаны к проверенным hostname этого проекта:

```powershell
& 'C:\AndroidProjects\qamqormed-app\scripts\Initialize-DataKeys.ps1' -CheckOnly
& 'C:\AndroidProjects\qamqormed-app\scripts\Invoke-Operator.ps1' -Action production-check
& 'C:\AndroidProjects\qamqormed-app\scripts\Show-DemoCredential.ps1' -Role patient
```

Последняя команда предназначена для вашей интерактивной консоли. `-Role doctor`
и `-Role admin` показывают по одному соответствующему тестовому аккаунту.
Не отправляйте показанные пароли в чат. Старый пароль подключения владельца БД
после переноса отозван; Netlify получает только `qamqor_runtime`, Production,
секретные Builds/Functions/Runtime. Не возвращайте старые значения из истории.
