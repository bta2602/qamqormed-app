## Блокеры выпуска

1. **Gemini в Netlify.** Локальный тест успешен по результату владельца,
   наличие ключа в Production подтверждено, но запрос через опубликованный
   обновлённый API ещё не проверен. Ключ Gemini не заменяет ключ шифрования БД.
   Сервер использует `GEMINI_API_KEY`, по умолчанию модель
   `gemini-3.5-flash-lite`; доступен серверный override `GEMINI_MODEL`.
   Актуальная инструкция: [GEMINI-SETUP-RU.md](GEMINI-SETUP-RU.md).
2. **Перенос шифрования.** Доступ к базе восстановлен после исправления
   опечатки в ID: правильно `mute-darkness-21400385`, а не `muted-darkness`.
   Требуются новая миграция ёмкости диагноза, ключи с защищённой резервной копией,
   тестовый перенос и проверка расшифровки перед рабочим окном. Наличие прежней
   отметки `20260925_data_protection` не означает шифрование данных.
3. **Остальные старые секреты.** Отзыв Google-ключа подтверждён владельцем.
   Исторический скан по-прежнему обнаруживает его строку
   в `42b629415068`, `netlify/functions/chat.mjs:30`. Значение не выводилось,
   не проверялось запросом к Google. История не переписывалась. Все 37 активных
   сотрудников всё ещё имеют пароли без корректного формата scrypt; ещё 6 таких
   аккаунтов принадлежат пациентам. Прежние раскрытые пароли нужно заменить
   с отзывом сессий; простое хеширование их не обезвреживает. Пароли не менялись.
4. **Идентификация для реальных данных.** Владелец подтвердил полностью
   вымышленные данные: дальнейший выпуск рассматривается только как демо.
   Знание ИИН/email и ручное одобрение восстановления всё ещё не доказывают
   личность для доступа к настоящим медицинским записям. Такой выпуск не разрешён.
5. **Сквозная проверка.** Публикация, проверка нового API и запуск обновлённого
   Android против него не выполнялись из-за перечисленных блокеров. Подключённого
   телефона/эмулятора нет. Рабочая публикация Netlify на момент проверки:
   `6ab56e794a8721498eb14385`, коммит `3b14cabb88d4a816c1519a2f2e102de2c265949e`.

Полный список ранее найденных рисков: [SECURITY-WORK-IN-PROGRESS.md](SECURITY-WORK-IN-PROGRESS.md).
Этот отчёт не снимает ни один непроверенный блокер из того списка.

## Следующие шаги

1. Подготовить `QAMQOR_DATA_KEY_ID` и `QAMQOR_DATA_KEYS` с криптографически
   случайным ключом и отдельной защищённой резервной копией. Gemini-ключ для
   шифрования не подходит. Production-ключам нужны Functions и Builds;
   не передавать значения в чат, Git или клиентские сборки.
2. Подготовить доверенную замену раскрытых паролей, отзыв сессий и перенос
   остальных активных паролей в scrypt. Не назначать общий пароль, не отключать
   пользователей и не удалять их записи без согласования.
3. Проверить новую миграцию и шифрование на изолированной ветке Neon;
   повторный сухой прогон должен показать `would_encrypt=0` и успешную расшифровку.
4. Проверить восстановление резервной копии и ключей по
   [DATA-PROTECTION-RU.md](DATA-PROTECTION-RU.md). Согласовать рабочее окно:
   старый сервер не должен читать или менять записи во время переноса.
5. Убедиться, что реальная проверка `db:check` проходит, а клиенты одной версии
   работают с тестовым API. Для тестового Netlify использовать отдельный ключ,
   не расширять область рабочего секрета на непроверенные Preview.
6. Пользователь разрешил публикацию при успешных проверках. Это условие пока
   не выполнено. После устранения блокеров подготовить проверенный коммит и
   публикацию. Не отключать `build:netlify` и не заменять его обычным `build`.
7. После публикации проверить новый API через тестовый аккаунт и обновлённый APK.
   Не отправлять реальные медицинские данные до завершения проверки владельцев.

Старая версия сервера не умеет читать новые зашифрованные поля. Откат после
переноса данных требует совместимого сервера и проверенной процедуры восстановления,
а не простого возврата старого Netlify-деплоя.
