# Обновление базы перед публикацией QamqorMed

Миграция - это SQL-инструкция, которая меняет структуру уже существующей базы.
Она добавляет серверные сессии, назначения лекарств и расписания приёма,
расширяет хранение паролей и проверяет связи записей с врачами.
Загрузка файла SQL в GitHub **не выполняет его в базе**.

## Почему Netlify может показать Deployment blocked

Сборка запускает `npm run db:check` до публикации сайта. Эта проверка только
читает служебную отметку миграции, индексы и структуру таблиц. Она не читает
записи пациентов, не выводит пароль и не применяет SQL автоматически.
Если миграции нет, база недоступна или переменная подключения отсутствует,
сборка остановится. Это ожидаемая защита от несовместимой публикации.

**Остановка новой сборки не отключает старый сайт и не устраняет его уязвимости.**
В старом публичном API обнаружена выдача паролей врачей и персональных данных.
До обновления ограничьте доступ к старому сайту/API средствами хостинга.
Не вызывайте старый `init-db`: он может изменять данные даже через GET.
Пароли затронутых врачей нужно заменить через доверенный административный
процесс, а их сессии отозвать до открытия обновлённого сайта.

## 1. Найдите именно существующую базу

В этом проекте используется Neon через `@netlify/neon` и серверную переменную
`NETLIFY_DATABASE_URL`. Откройте подключение Neon в настройках сайта Netlify
либо войдите в [консоль Neon](https://console.neon.tech/).

Выберите проект, базу и ветку, которые использует опубликованный сайт.
Не создавайте новую пустую базу через `init-db` или `netlify database init`.
Не переходите на другой провайдер и не меняйте строку подключения ради миграции.
Если непонятно, где база, пришлите скриншот панели подключения с закрытыми
секретами и персональными данными. Пароль или URL подключения присылать не нужно.

## 2. Сделайте резервную копию и проверку

1. Остановите изменения данных через старый сайт/API на время обновления.
2. Сделайте резервный снимок базы или защищённый PostgreSQL backup. Убедитесь,
   что умеете восстановить его, и сохраните идентификатор текущей публикации.
3. Создайте из текущего состояния базы отдельную тестовую ветку Neon и сначала
   проверьте SQL на ней. Это копия данных, а не новая пустая база; не публикуйте
   её содержимое и не используйте её URL вместо production.
4. Выполните SELECT-проверки из раздела **Backup and preflight** в
   [полной инструкции](DEPLOYMENT-2026-09.md). При дубликатах email/записей,
   неверных связях врача или несовместимой структуре остановитесь. Не удаляйте
   данные автоматически для обхода ошибок.

## 3. Выполните файл целиком

1. Откройте в репозитории
   [migrations/20260924_sessions_prescriptions.sql](migrations/20260924_sessions_prescriptions.sql).
   Кнопка **Raw** показывает SQL без оформления GitHub.
2. В Neon откройте **SQL Editor**. Ещё раз проверьте выбранные ветку и базу.
3. Поместите в редактор весь SQL: от `BEGIN;` до последнего `COMMIT;`.
   Запустите весь блок кнопкой **Run**, без выделения отдельной строки.
4. Если есть ошибка, не продолжайте и не убирайте ограничения из файла.
   После ошибки транзакции выполните `ROLLBACK;` в том же соединении, если
   редактор сохраняет его. Сообщите текст ошибки без данных пациентов/паролей.
5. На тестовой ветке проверьте повторный запуск: он не должен дублировать данные.
6. Только после успешной проверки, резервного копирования и сверки production
   повторите полный SQL на рабочей ветке при остановленных изменениях данных.

Файл не содержит `DROP TABLE`, удаления пациентов или назначений. Он работает
в транзакции: при конфликте миграция должна откатиться, а не угадывать связь.
Но изменение индексов может блокировать запросы, поэтому нужна пауза в работе.

После успешного выполнения проверьте служебную отметку:

```sql
SELECT version, applied_at
FROM qamqormed_schema_migrations
WHERE version = '20260924_sessions_prescriptions';
```

Должна появиться одна строка. **Не добавляйте её вручную**: это подтверждение
успешного выполнения всего SQL, а не переключатель для обхода проверки.
Используйте актуальный файл из этого репозитория: ранний ZIP мог содержать
миграцию без этой отметки. Полный актуальный SQL допускает повторный запуск.

## 4. Возобновите публикацию Netlify

1. Сначала завершите замену скомпрометированных паролей и отзыв сессий,
   описанные в `DEPLOYMENT-2026-09.md`. Обычный перенос паролей в хеши не
   обезвреживает уже раскрытые пароли.
2. Убедитесь, что существующая `NETLIFY_DATABASE_URL` доступна и сборке,
   и Functions в нужном контексте Netlify. Это секретная настройка сервера:
   не записывайте её в Git, `netlify.toml`, HTML или Android.
3. В Netlify откройте **Deploys**, затем повторите неудачную сборку текущей
   ветки `main` (**Retry deploy** / **Trigger deploy**, название зависит от UI).
4. Дождитесь сообщения `Database schema ready` и успешной публикации. Изменение
   БД само по себе не запускает новую сборку GitHub/Netlify.
5. До открытия доступа проверьте вход, выход, запись к врачу и назначения
   на разрешённых тестовых аккаунтах. Проверьте, что публичный каталог больше
   не отдаёт пароли, email и ИИН; не публикуйте ответы старого API.

Если проверка не проходит после SQL, причина может быть в выбранной ветке БД,
недоступности соединения или области действия переменной. Не отключайте
`db:check` и не заменяйте безопасный `publish = "public"` на корень проекта.

## Что не происходит автоматически

- GitHub не применяет SQL к Neon.
- Сборка не делает резервную копию и не меняет пароли.
- Сборка не подключает FCM, отправку почты или почтовые коды подтверждения.
- Успешные локальные тесты не подтверждают состояние рабочей базы.
